# AGENTS.md

## Repository purpose

A personal tooling collection: curated developer tool references (`README.md`), bash config backups, OpenCode config backup, Claude config backup, and a fresh-Linux bootstrap guide.

No build system, no tests, no CI. All content is documentation and shell scripts.

## Install commands

| What | Command |
|------|---------|
| Bash aliases + functions | `cd bashrc-backup && bash install.bash` |
| OpenCode config | `cd opencode-backup && bash install.sh` |
| Claude Code config | `cd claude-backup && bash install.sh` |
| Local llama.cpp (Vulkan) | `cd llama.cpp && cp config.env.example config.env && bash bootstrap.sh` |

- `bashrc-backup/install.bash` deletes the `# CUSTOM START` … `# CUSTOM END` block from `~/.bashrc`, appends the new block at the end, then calls `exec bash -l` to reload the shell.
- `opencode-backup/install.sh` copies `opencode.jsonc` to `~/.config/opencode/opencode.jsonc`, `AGENTS.md` to `~/.config/opencode/AGENTS.md`, any `agents/*.md` to `~/.config/opencode/agents/`, and `skills/*/` to `~/.config/opencode/skills/` (creates dirs if needed). Add-only: existing agents/skills/plugins from other sources are kept. It ships **no plugin** — the bash guard comes from `stadtwerk_ai_config` (see below).
- `claude-backup/install.sh` copies `settings.json`, `settings.local.json`, `mcp.json`, `commands/`, and `skills/` into `~/.claude/`. Note: `settings.local.json` is in `.gitignore` and won't be present in a fresh clone — the script will fail on that step; ignore or create an empty file first.

## OpenCode config notes

- No global default `model` is pinned in `opencode.jsonc` (pick per session).
- `opencode-backup/AGENTS.md` → `~/.config/opencode/AGENTS.md` holds the **global personal rules** (currently: German conversation / English artefacts, the human-vs-agent writing register, measured-vs-guessed numbers, cleaning up processes and temp files you started, and verifying documented values against the live system with read-only commands). Global and project rules are separate categories in OpenCode, so this file is loaded *in addition to* a project's own `AGENTS.md`, in every session. That is deliberate: a preference that must hold for every edit belongs here and not in a skill, because skills only enter context when their `description` matches and they are known to undertrigger. Keep the file short — it costs context in every session.
- Two llama.cpp providers: `lieselotte` (local, `127.0.0.1:8081`) and `hermine` (remote, `hermine:8081`). Model IDs are bare aliases without the `.gguf` suffix.
- `lieselotte` models: `Qwen3.6-27B`, `Qwen3.6-35B-A3B`, `gemma-4-26B-A4B`, `ornith-1.0-9b`, `ornith-1.0-35b`, `Qwen-AgentWorld-35B-A3B`, `gemma-4-31B`, `Laguna-XS-2.1`. `hermine` models: all eight are active sections in hermine's `presets/models.ini` and whitelisted in `opencode.jsonc`, but only five GGUFs are actually on that box — `Qwen3.6-27B`, `Qwen3.6-35B-A3B`, `gemma-4-31B`, `Laguna-XS-2.1`, `gemma-4-26B-A4B` (verified 2026-08-05). Requesting either Ornith or `Qwen-AgentWorld` there will fail to load until the weights are downloaded. The untuned sections correlate exactly with the missing weights: all three still carry lieselotte's Vulkan defaults (mixed `q8_0`/`q4_0` KV, unmeasured `ctx-size = 262144`), because nothing can be measured without the file.
- Qwen3.6-27B (unsloth `-MTP-` build, `IQ4_XS`): the MTP speculator ships inside the GGUF, so `spec-type = draft-mtp` needs **no** `model-draft`. Presets differ per machine: **hermine** (RTX 4090, 23028 MiB, CUDA) `ctx-size = 131072`, KV `q8_0`/`q8_0`, `spec-draft-n-max = 3` — measured 2026-08-04 at 21877 MiB peak (~1.1 GiB free), 2516 t/s prompt / 97 t/s generation; **lieselotte** (7900 XTX, Vulkan) `device = Vulkan0`, `ctx-size = 262144`, KV `q8_0`/`q4_0`, `spec-draft-n-max = 4`. Sampling: the card gives two thinking-mode sets — `temp 1.0` for general tasks and `temp 0.6` for precise coding — both with `top-p 0.95`, `top-k 20`, `min-p 0.0`, `presence-penalty 0.0`; hermine's preset uses the 0.6 coding set, lieselotte still uses 1.0. hermine additionally chains a second, draft-model-free speculator: `spec-type = draft-mtp,ngram-mod` with `spec-ngram-mod-n-match/min/max = 24/48/64` (these three equal the build's defaults and are written out only to be explicit). ngram-mod is a 16 MiB host-RAM hash table (no VRAM) that hashes the last 24 tokens and chains up to 64 drafted tokens, discarding the draft entirely if the chain breaks before 48 — so it pays off on verbatim repeats (file rewrites, quoted diffs) and stays silent on novel text. Priority is **hardcoded in llama.cpp, not list order** (`common/speculative.cpp` `common_speculative_init`): all `ngram-*` implementations run before all `draft-*`, so MTP only drafts when ngram-mod returns nothing. Enabling it also raises the global draft budget to 64 via `common_speculative_n_max`, which enlarges the verification batch. Speed impact on hermine is **unmeasured** — the 97 t/s above predates it. `fit = off` is set deliberately although it is nearly a no-op here (`--fit` only adjusts arguments left unset, and this section sets `ctx-size`/`n-gpu-layers` itself); the real effect is that a VRAM shortfall now fails loudly instead of silently shrinking, which matters because the measured peak leaves only ~1.1 GiB free.
- Qwen3.6-35B-A3B (unsloth `-MTP-` build, `UD-IQ4_XS`, 18.2 GB on disk): 35B-A3B MoE (arch `qwen3_5_moe`, 40 layers, 256 experts + 1 shared, 8 routed active, native 262k ctx). Hybrid layout `10 × (3 × Gated-DeltaNet → MoE → 1 × Gated-Attention → MoE)` means only 10 of 40 layers carry a growing KV-cache (2 KV heads, head dim 256), which is why 262k ctx is affordable at `q8_0`. MTP ships inside the GGUF, so `spec-type = draft-mtp,ngram-mod` needs no `model-draft`. **Measured** on hermine with `llama-fit-params` 2026-08-04 at `ctx-size = 262144` + `q8_0`/`q8_0` + `flash-attn on`: model 16435 + KV 2782 + compute 820 = **20037 MiB of 23027** (~2990 MiB free), plus 515 MiB model / 264 MiB compute on the host. That figure **excludes the MTP context** — `llama-fit-params` rejects `--spec-type`, so the real peak is higher and remains unmeasured; the ~2.9 GiB headroom is the reason 262144 is kept anyway. `cache-type-k/v-draft = q4_0` is set, but note it was added on the assumption that it saves VRAM, and the gemma-4-31B measurement below disproves that for MTP drafters generally — it is kept because it is free, not because it was measured to help here. Sampling: the card gives three **whole** sets and they are not to be mixed — thinking/general `temp 1.0` + `presence-penalty 1.5`, thinking/precise-coding `temp 0.6` + `presence-penalty 0.0`, instruct `temp 0.7` + `presence-penalty 1.5` (all three share `top-p` 0.95/0.95/0.80, `top-k 20`, `min-p 0.0`). The presets use the coding set whole. Pulling only the `1.5` into it would be a combination the vendor never publishes, and it is wrong on the merits: a presence penalty punishes repeated tokens, which is precisely what code consists of, and the card warns that higher values can cause language mixing. The one place the two models differ is the *general* set — 35B uses `presence-penalty 1.5` there, 27B uses `0.0` — so that difference is invisible as long as both run the coding set. The presets use the coding set — before this change both `models.ini` and `models.example.ini` set **no sampling at all** for this model and silently ran llama.cpp's defaults (`temp 0.8` / `top-p 0.9` / `top-k 40`), which contradicts the card. It is also a VLM, but no `mmproj-*.gguf` is present in the model directory, so the presets are text-only.
- Ornith-1.0 (DeepReinforce/ornith-ai, MIT, agentic coding): post-trained on Gemma 4 and Qwen 3.5, so the 9B reports arch `qwen35` — which is why its sampling looks like Qwen's. It is not copied: the card recommends `temp 0.6`, `top-p 0.95`, `top-k 20` verbatim (and `temp 1.0` only to reproduce the published benchmarks), so the values already in both presets are vendor-correct. A reasoning model — the assistant turn opens with `<think>…</think>` by default, and the vendor's serving recipes add a reasoning parser plus a `qwen3_xml`/`qwen3_coder` tool-call parser, which `jinja = true` + `reasoning-format = auto` cover. Unlike Laguna the embedded template does **not** default thinking off, so no explicit `reasoning = on`. **9B measured on hermine 2026-08-05** by loading at the full native `ctx-size = 262144`, KV `q8_0`/`q8_0`: **14958 MiB of 23028** (~8066 MiB free), 75.3 t/s generation. No MTP drafter exists for it, so `llama-fit-params` is complete here rather than a lower bound — and its estimate (13783 MiB) came within ~1.2 GiB of the real load. The 8 GiB left idle cannot be turned into context (262144 is already `n_ctx_train`) and not into a better quant either: BF16 is 17.9 GB and would need ~23.8 GB with this KV cache. Two runs bracket what `ngram-mod` is worth on novel text — 75.30 t/s with it against 75.32 t/s without, i.e. nothing, exactly as the mechanism predicts. `cache-type-v` was `q4_0` (lieselotte's Vulkan floor) and is now matched to K on hermine. The 35B is still on unmeasured Vulkan defaults.
- `cache-reuse` is **inert on this llama.cpp build (10243) — everywhere, not per model.** Every load logs `cache_reuse is not supported by this context, it will be disabled`. Measured 2026-08-05 across four architectures (gemma4 dense 31B, gemma4 MoE 26B-A4B, qwen35 dense 9B, Qwen3.6-27B) and, on the 9B, across five flag combinations: with speculative decoding, without it, `-fa off`, KV `f16` instead of `q8_0`, and `--kv-unified`. All disabled. So it is neither the hybrid-attention architecture nor speculative decoding nor FlashAttention, as was assumed twice before this was tested properly. The key is still written into every section because it costs nothing and would start working on a build that supports it — but do not credit it with anything, and do not let the llama-preset skill's description of it ("reuses cached KV for repeated prefixes across turns") be read as a statement about this machine.
- Laguna XS 2.1 (poolside, OpenMDW-1.1, agentic coding): 33B-A3B MoE (arch `laguna`, 40 layers, 256 experts + 1 shared, native 262k ctx). Mixed attention layout — 10 global-attention layers + 30 sliding-window (512) layers in a 3:1 ratio with sigmoid gating and per-layer rotary scales — so only a quarter of the layers carry a growing KV-cache and long contexts stay cheap on VRAM. Built for long-horizon agent work (SWE-bench Verified 70.9, SWE-bench Multilingual 63.1, Terminal-Bench 2.0 37.5). Reasoning is interleaved between tool calls, and the model expects *preserved thinking* (prior assistant `reasoning_content` kept in the message history) → `jinja = true` + `reasoning-format = auto`, and clients that drop thinking blocks will see it stop reasoning in follow-up steps. **Thinking is not on by default in this GGUF**, contrary to what the card implies: the embedded template opens with `{%- set enable_thinking = enable_thinking | default(false) -%}` (verified 2026-08-04 by reading the template out of the GGUF metadata — note it sits past the 100 MB mark, a `strings` window of a few MB misses it entirely). Only under `enable_thinking` does the template render `<think>` + `reasoning_content` + `</think>` for *every* history message, which is exactly the preserved thinking the agent loop needs; the else branch emits a bare `</think>`. hermine's preset therefore sets `reasoning = on` explicitly rather than trusting `--reasoning auto` to flip it. Whether `auto` would have flipped it anyway is **unverified** — the template default is the measured fact, the behaviour of `auto` against this template is not. If a rendered prompt ever shows thinking still off, `chat-template-kwargs = {"enable_thinking": true}` sets the template variable directly. Whether the template declares `supports_preserve_reasoning` (what `--reasoning-preserve` looks for) is also unverified: the string is absent from a `strings` dump, but that dump was not a structured metadata read. Upstream llama.cpp support merged via PR #25165 (2026-07-22). Preset uses bartowski's imatrix `IQ4_XS` (18.2 GB) for KV/compute headroom on a 24 GB card. hermine runs `ctx-size = 163840` with KV `q8_0`/`q8_0` — **measured** with `llama-fit-params` 2026-08-04: model 17259 + KV 3463 + compute 837 = 21559 MiB of 23027 (~1468 free). The neighbouring points were measured too: 131072 → 20719 (2308 free), 196608 → 22399 (628 free), 262144 → 24079, which does **not** fit. 163840 was chosen over 196608 because 628 MiB is as thin as the gemma-4-31B section that this file already flags as a low-margin gamble. Unlike the Qwen sections these figures are complete rather than a lower bound, because Laguna has no MTP drafter and `ngram-mod` needs no context of its own. The previous `ctx-size = 32768` was pure caution and cost a factor of five. Its KV pair was also the mixed `q8_0`/`q4_0` that collapses throughput on this CUDA box (see the note further down), so both were wrong at once. Vendor sampling (the only preset the card documents, used for all published benchmarks): `temp 1.0`, `top-p 1.0`, `top-k 20`. A DFlash speculator exists (`poolside/Laguna-XS-2.1-DFlash`) and the build advertises `--spec-type draft-dflash`, but no GGUF in llama.cpp's own `dflash` arch was found — so no *draft-model* speculator is wired. It does run `spec-type = ngram-mod`, which needs no draft model at all, making that the only speculator this model can currently use.
- Qwen-AgentWorld-35B-A3B (Qwen, Apache-2.0, language world model): 35B-A3B MoE (arch `qwen35moe`, base Qwen3.5-35B-A3B) that simulates 7 agent environments (MCP/Search/Terminal/SWE/Android/Web/OS) via long CoT. Hybrid attention (10×(3× Gated-DeltaNet → 1× Gated-Attention)) means only ~10 of 40 layers carry a growing KV-cache, so long contexts are cheap on VRAM. `UD-IQ4_XS` (17.8 GB) full-GPU on the 7900 XTX (`device = Vulkan0`); `q8_0` KV fits the native 262k ctx (drop to 131072 if OOM). Thinking mode on by default → `jinja = true`. Vendor sampling: `temp 0.6`, `top-p 0.95`, `top-k 20`.
- Gemma 4 31B (Google/unsloth, Apache-2.0, dense QAT VLM): dense 31B (arch `gemma4`, 60 layers, native 256K ctx). Hybrid attention interleaves local sliding-window (1024) layers with periodic global layers (unified K/V + Proportional RoPE), so the growing KV-cache lives only in the few global layers → long contexts are cheap on VRAM. Quantization-aware-trained `UD-Q4_K_XL` (17.3 GB) keeps near-bf16 quality and fits a 24 GB card alongside the ~280 MB MTP drafter `mtp-gemma-4-31B-it.gguf`. MTP speculative decoding is wired via `spec-type = draft-mtp` + `model-draft = …/mtp-gemma-4-31B-it.gguf` (lossless — the target verifies every drafted token). Presets differ per machine: **lieselotte** (7900 XTX, Vulkan) `device = Vulkan0`, `ctx-size = 163840`, KV `q8_0`/`q4_0`, `spec-draft-n-max = 4`; **hermine** (RTX 4090, 23028 MiB, CUDA) `ctx-size = 65536`, KV `q8_0`/`q8_0`, `spec-draft-n-max = 3` — measured 2026-08-04 at 22467 MiB peak (~560 MiB free), 2391 t/s prompt / 86 t/s generation. Native max is 262144, but on hermine `llama-fit-params` caps a V-`q8_0` run at 58624 with its default 1 GiB margin; the KV cache is preallocated in full at load, so 65536 is a deliberate low-margin choice that assumes nothing else claims VRAM. Text+Image via optional `mmproj = …/mmproj-F16.gguf`. Vendor sampling: `temp 1.0`, `top-p 0.95`, `top-k 64`; thinking is opt-in via a `<|think|>` token → `jinja = true`. Two follow-ups from the 26B-A4B work were settled here by measurement on 2026-08-05, five real loads at ctx 65536: **`cache-type-k/v-draft` saves no VRAM at all** — 22265–22269 MiB at load and 22277–22281 MiB after generation, identical to within 4 MiB whether the draft cache is f16 or `q4_0`. The assumption behind adding it (a separate drafter cache sitting next to the target's) is wrong for MTP: the drafter shares the target's KV cache, which is what the 26B's card states outright. It is set to `q4_0` anyway because it costs nothing and generation was faster in all three `q4_0` runs (80.45 / 80.00 / 72.41 t/s) than in both f16 runs (66.90 / 69.20), tracking draft acceptance (0.849 / 0.849 / 0.727 against 0.656 / 0.684). **Do not quote a percentage**: an initial pair of bit-identical `q4_0` runs suggested a clean +16 %, and the third run landed between the two clusters, so n is too small and the spread too wide for anything beyond "not slower, probably a little faster". All five prompts were the same short one, so the prompt-throughput figures (133–169 t/s) are not comparable to the 2391 t/s above, which used a large prompt. `cache-reuse = 256` is **inert** here too — `cache_reuse is not supported by this context, it will be disabled` in 5 of 5 logs — which later turned out to be true of every model on this build, see the dedicated bullet below. `ctx-size` stays 65536: nothing was freed that could be spent on context, and 22281 MiB leaves only 747 MiB.
- Gemma 4 26B A4B (Google/unsloth, Apache-2.0, MoE QAT VLM): 25.2B total / 3.8B active MoE (arch `gemma4`, 30 layers per the card but `n_layer 31` in the GGUF, 8 of 128 experts active + 1 shared, sliding window 1024, native 256K ctx). Same hybrid attention as the 31B, and the load log shows the consequence directly — `llama_kv_cache: layer 3: sharing with layer 29` — which is why the full native context is affordable. `UD-Q4_K_XL` (13.3 GB) plus the 252 MB drafter `mtp-gemma-4-26B-A4B-it.gguf`. **The drafter was the find**: the card documents `--spec-type draft-mtp --spec-draft-n-max 4`, but only the main GGUF had been downloaded and `models.list` carried a single line for this repo, so `recommend.sh` correctly reported "no MTP head found" and the section ran `ngram-mod` alone. Both are fixed. Measured on hermine 2026-08-05 by actually loading the server at `ctx-size = 262144`, KV `q8_0`/`q8_0`, draft KV `q4_0`/`q4_0`, `spec-draft-n-max = 4`: **21193 MiB peak of 23028** (~1835 MiB free), **8109 t/s prompt** (7828-token prompt), **234.6 t/s generation** (400 tokens), and MTP **draft acceptance 0.751** with mean draft length 3.99 — the budget of 4 is fully used, so it is not set too high. After a long prompt acceptance drops to 0.547 / mean 3.13 and generation to 158.6 t/s. Roughly 3× the 31B's prompt and 2–3× its generation throughput at 3.8B active parameters, and unlike the 31B it holds the full 262144 rather than 65536. Two caveats on those numbers: the runs where generation was exercised omitted `cache-reuse` and read 20766–20778 MiB, ~430 MiB below the load that included it — **unexplained**, and the higher figure is quoted because it matches the written section. And `llama-fit-params` alone had reported 18031 + 240 MiB, a lower bound, because it cannot size a separate drafter's context; only the real load settles it. Sampling is one single published set for all use cases — `temp 1.0`, `top-p 0.95`, `top-k 64` — already in the section. **Thinking must not be forced on here.** `recommend.sh` flagged that the template consumes `reasoning_content` from history and suggested `reasoning = on`, as with Laguna; the card says the opposite in so many words ("Thoughts from previous model turns must *not be added* before the next user turn begins") and makes thinking opt-in per request via a `<|think|>` token in the system prompt. So this is not the Laguna case, `reasoning = on` stays out, and `jinja = true` + `reasoning-format = auto` are enough. `cache-reuse = 256` is kept but is **inert**: the server logs `cache_reuse is not supported by this context, it will be disabled`. It is left in so it starts working if a future build supports it — the limitation turned out not to be architectural at all, see the dedicated bullet below. Text+Image per the card (~550M vision encoder), but no `mmproj-*.gguf` is present, so the preset is text-only.
- Enabled providers: `lieselotte`, `hermine`, `anthropic`, `openrouter`
- `openrouter` is the built-in OpenRouter provider (models preloaded from Models.dev); its API key is read from the `OPENROUTER_API_KEY` env var via `"apiKey": "{env:OPENROUTER_API_KEY}"` instead of `/connect`
- Plugin (npm): `opencode-claude-auth@latest`; `share: disabled`
- Bash guard: **no longer shipped from this repo.** The merged `command-guard.js` lives in `stadtwerk_ai_config/.opencode/plugin/`; that repo's `install-opencode.sh` drops it into the same `~/.config/opencode/plugin/`, so it applies in every project. It hooks `tool.execute.before`, **normalises** each command (strips `env`/`sudo`/`nice`/`timeout` wrappers, resolves absolute paths & `$(which x)` to bare verbs, strips `.exe`, decodes base64 as UTF-8 *and* UTF-16LE for PowerShell's `-EncodedCommand`, reads here-docs, re-scans `-c`/`-Command` payloads of sh/python/node/powershell/cmd) and **recursively splits** it across pipes/`&&`/`;`/subshells before matching — which is what closes the string-glob bypasses the wren.wtf "Stop Using OpenCode" post calls out. Rules are **embedded in the `.js`** (an external rule file would not survive: the team installer copies `plugin/*.js` only, and a missing rule file used to disable guarding silently) and are **deny-only**. The ask tier belongs to the team config, because a plugin cannot prompt: the `permission.ask` hook is declared in `@opencode-ai/plugin` 1.14.20's types but has **zero dispatch sites** in the opencode 1.18.12 binary (verified by enumerating every `trigger("…")` literal). Fail-closed twice: destructive + undeterminable context, and base64-for-a-shell that will not decode. Health signal: the toast **"Löschschutz aktiv"** at startup plus `echo guard-selftest`, which must be blocked — a plugin that fails to load cannot warn about itself, so only a positive signal makes its absence detectable. Verified 2026-08-04: 33/33 unit cases, and 0 false positives across 2253 distinct real commands from this machine's log. Not a sandbox — it cannot see inside a shell script it invokes, and writing *about* its rules in a here-doc can trip them.

## llama.cpp config notes

- Linux/Pop!_OS adaptation of `countzero/windows_llama.cpp`; **Vulkan** backend, **prebuilt** binaries (no compiler/conda).
- Scope: run already-built GGUF models only (no quantization/conversion).
- `bootstrap.sh` downloads `llama-<tag>-bin-ubuntu-vulkan-<arch>.tar.gz` into `vendor/` (idempotent, `--force` to reinstall).
- `download-model.sh` pulls GGUFs to `$LLAMA_MODELS_DIR` (default `~/.local/share/llama.cpp/models`, outside the repo); prefers `hf`/`huggingface-cli`, falls back to `curl`; manifest `models.list`.
- `server.sh`: router mode (default, `presets/models.ini`) or single model; serves OpenAI-compatible API at `LLAMA_HOST:LLAMA_PORT` (default `127.0.0.1:8081`).
- `LLAMA_VERSION` defaults to `latest`. `server.sh`/`server.ps1` auto-run `bootstrap.*` before serving to pick up new releases, throttled by a `vendor/.last-auto-check` marker (`LLAMA_UPDATE_CHECK_INTERVAL`, default 3600s) so repeated restarts don't hit GitHub's API. `LLAMA_AUTO_UPDATE=0` disables it (offline use); a failed check falls back to the already-installed build instead of hard-failing.
- Config in `config.env` (gitignored; copy from `config.env.example`). On the Windows host there is no `config.env` — it configures itself in `config.ps1` (also gitignored, and it holds a plaintext `HF_TOKEN`). All four bash entry points therefore load their settings through `config-load.sh`, which resolves env var > `config.env` > `config.ps1` > `config.env.example`. Before that existed, `server.sh`, `download-model.sh` and `bootstrap.sh` were **completely broken on hermine** (verified 2026-08-05): they fell through to `config.env.example`, which carries CRLF, and `source` then fails on every line with `$'\r': command not found`. Falling through was wrong twice over — that file also assigns a Linux models path and `LLAMA_BACKEND=vulkan`, so a working `source` would have pointed at a nonexistent directory and fetched a Vulkan build for a CUDA box. `recommend.sh` keeps its own copy of this logic on purpose: it must run standalone from the skill directory.
- Two WSL-on-Windows traps when testing a server by hand on hermine, both cost a wasted run: `--host 127.0.0.1` binds the *Windows* loopback and is unreachable from WSL (use `0.0.0.0` plus the gateway IP from `ip route`; the name `hermine` does **not** resolve from inside WSL on hermine itself, only from the LAN). And `nohup ./llama-server.exe &` returns the *bash* PID — `taskkill /PID` on it leaves the Windows process alive holding VRAM, which then makes the next start fail with `failed to load draft model`. Kill by image name (`taskkill /F /IM llama-server.exe`) and wait for `nvidia-smi` to drop.
- On CUDA (hermine), `cache-type-v` MUST equal `cache-type-k`. Measured 2026-08-04 with gemma-4-31B @ 65536 + MTP: matched `q8_0`/`q8_0` yields 2391 t/s prompt / 86 t/s generation, the mixed `q8_0`/`q4_0` pair collapses to 32 t/s / 9 t/s because it falls off the fused FlashAttention kernel. Untested on Vulkan (lieselotte), whose presets still use the skill's `q8_0`/`q4_0` floor — so the llama-preset skill's V-floor is not safe to apply blindly on the CUDA box.
- `spec-type` carries `ngram-mod` in **every** section of both `presets/models.ini` and `presets/models.example.ini` (8 each) — as `draft-mtp,ngram-mod` where an MTP drafter exists, as bare `ngram-mod` where none does (both Ornith, Qwen-AgentWorld, Laguna). It needs no draft model and no VRAM, and speculative decoding is lossless, so a bad fit costs speed and never output quality. The gain is **unmeasured on both machines** — adopted from countzero's 24 GB preset on mechanism. Expect it to pay off on file-rewrite-heavy agent turns and to do nothing on novel prose, where the 48-token minimum chain length suppresses the draft entirely. `cache-ram = 16384` is set on hermine's three agentic-coding sections (both Qwen3.6 and Laguna) and nowhere else: the default is 8192, the box has 39 GB, and the value applies **per loaded model**, so raising `models-max` above 1 multiplies it.
- Models are **never** committed: `.gitignore` excludes `llama.cpp/{vendor,cache}/`, `config.env`, `presets/models.ini`, and `**/*.gguf`.
- OpenCode: the local `lieselotte` provider `baseURL` is `http://127.0.0.1:8081/v1`; the remote `hermine` provider points at `http://hermine:8081/v1`.
- Skill `.opencode/skills/llama-preset/` (`scripts/recommend.sh`) — **moved out of `.claude/skills/` on 2026-08-04 and substantially rewritten.** It generates/updates a `presets/models.ini` `[section]` from measured hardware (`llama-server --list-devices`, `llama-fit-params`, iGPU deprioritized) plus agentic defaults. What changed and why, because each item was a real defect found by testing it against this machine rather than reading it:
  - It was **invisible to OpenCode**: its `description` was 1371 characters against a documented 1024 limit, so it never appeared in `<available_skills>` while `commit-push` in the same directory did. Now 984. Every session before this one ran without it, which is the likeliest reason the presets had drifted so far.
  - `cache-type-v = q4_0` was a global "floor". On CUDA that is the mixed pair that collapses throughput 9× (see the note above), and the skill would have regenerated it. The V type is now **backend-derived** from the device id: `q4_0` on Vulkan, matched to K everywhere else.
  - `spec-type` knew only `draft-mtp` from a hardcoded list. Both the allowed KV types and the speculator list are now **parsed out of `--help`**, so a newer llama.cpp unlocks better defaults with no edit — the point of keeping this box's server current. `ngram-mod` is chained in whenever the build offers it.
  - Nothing inspected the **embedded chat template**, so Laguna's `enable_thinking | default(false)` was invisible. The script now scans it (200 MiB window — the template sits past the tensor-name table) and reports thinking/preserved-reasoning findings instead of silently accepting the card's claim.
  - It could not run on hermine at all: `resolve_bin` matched only `llama-server`, and sourcing the CRLF `config.env.example` broke bash. Worse, passing a `/mnt/c/...` path to the Windows `.exe` makes `llama-fit-params` print its header and **no data line** — a silent failure the script read as "does not fit" and turned into `ctx-size = 4096` for a model that measurably does ~160k. Paths are now converted via `wslpath -m`, config precedence is env > `config.env` > `config.ps1` > `.example`, and CR is stripped.
  - Section names were derived from the GGUF filename (`[Laguna-XS-2.1-IQ4_XS.gguf]`) rather than the bare alias, so every existing model looked new. Combined with a CRLF-blind `$0==sec` match in the merge, `--write` would have appended a **duplicate** section.
  - `--write` **deleted keys it does not manage.** Sampling, `reasoning` and `cache-ram` showed up in the diff as "no longer set" and would have been dropped. They are now carried over verbatim and reported as `= key (kept)`. The merge also replaces in place instead of moving the section to the end of the file, because section order is maintained by hand.
  - `n-cpu-moe` is now **opt-in** (`--allow-cpu-moe`). It used to buy native context by pushing experts to host RAM, which puts a PCIe round trip in the generation path — the wrong trade for long agent sessions. Default is to shrink `ctx-size` until everything is GPU-resident.
  - Sampling guidance changed from "prefer the lower temperature" to "adopt one published set whole, never mix values across sets", which is the rule that keeps a general-set `presence-penalty 1.5` out of a coding preset.
  - A sibling `mtp-*.gguf` counted as a name match, so the moment a model *had* its drafter on disk it became unreachable by alias: `recommend.sh gemma-4-26B-A4B` died with "Ambiguous model", and `gemma-4-31B` had the same defect all along. Drafters are now excluded from target resolution unless asked for by exact filename — the script looks for them a few steps later anyway.
  - `presets/models.example.ini` contained a **duplicate** `[gemma-4-26B-A4B]`, byte-identical, at two positions. Removed the earlier one so the remaining position matches `models.ini`'s hand-maintained order (both files now list the same eight sections in the same sequence). This is the failure mode the CRLF-blind section match used to produce, so it is worth re-checking after any `--write`.
  Validation: run against `Laguna-XS-2.1` on hermine it independently produced `ctx-size = 159744` versus the 163840 chosen by hand — one 4096 step apart, from an independent path. Still not automated: reading the model card, weighing the VRAM margin, and deciding on the template finding. `temp = 0` remains refused without `--zero-temp-ok`; OCR models (section name matches "ocr") keep conservative defaults; vendor keys arrive via `--extra KEY=VALUE` and never override a hardware/agentic-owned key.

## Conventions

- This repo is a dotfiles/config backup, not a software project. Do not add build tooling or tests.
- `.gitignore` excludes `.claude/settings.local.json`, `.playwright-mcp`, and the llama.cpp `vendor/`, `cache/`, `config.env`, `presets/models.ini`, and `*.gguf`.
- Fresh machine setup order: SSH → clone repo → `bashrc-backup/install.bash` → Claude Code → `claude-backup/install.sh` → `opencode-backup/install.sh` → authenticate MCPs → (optional) `llama.cpp/bootstrap.sh`.
- Any work on `llama.cpp/presets/*.ini` — adding a section, retuning an existing one, or diagnosing a model's context/speed — goes through the `llama-preset` skill (`.opencode/skills/llama-preset/`) **first**. This bullet exists because description-based skill triggering undertriggers while an `AGENTS.md` line is loaded in every session; the skill is also project-local, so it is invisible outside this repo. Do not hand-write a preset value that `recommend.sh` would have measured — and do overrule the script when a hand measurement contradicts it, recording both numbers. Measuring throughput of an already-configured model belongs to the neighbouring skill `tilloh-local-llm-bench` instead.
- Verification here is cheap in consequence and expensive in time: loading a 16 GB model and reading `nvidia-smi` costs minutes but changes nothing. Spend those minutes instead of asking. Ask first only when verifying means stopping something the user is currently running (a live `llama-server`, for instance).
- Prefer running the tool that reports a number over deriving it by arithmetic. `llama-fit-params` plus a real prompt run beats KV-per-token estimates — the estimates were wrong by enough to matter. A measurement that contradicts your model of the system is the interesting result, not an error to explain away.
- State what you could not verify rather than smoothing over it. Numbers that hold on one machine and were never tested on the other are marked as untested (e.g. whether the mixed-KV collapse also affects Vulkan/lieselotte). An unverified claim presented as fact is worse than an admitted gap, because the next reader has no way to tell.
